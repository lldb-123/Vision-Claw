## 4. 机械方案的当前理解

**用户已经确认的是推拨物体后下落。** 更具体的结构来自队内草稿，目前理解如下：

1. 框架内部沿高度分为上下两层，上层为放置待分拣物体的托盘。
2. 托盘左下方设下落孔。
3. L 形直角挡板移动到物体附近，将物体沿托盘拨向下落孔，可能包含挡板升降动作。
4. 下层为带多个储物容器的转盘，先使目标盒对准下落孔，再让物体落下。
5. 相机拟从上方观察托盘，具体安装位置尚未核实。

实际轴数、哪台电机驱动哪个部件、挡板接触点、下落孔位置与直径、转盘原点和盒号方向都未取得准确资料。材料表中的电机数量也不能直接推导这些对应关系。

草稿提出从左下向右上处理物体，当前程序也按图像中较靠下、再靠左的顺序选择候选。但这个顺序本身不能保证拨板不会碰到其他物体，拥挤摆放时仍需要机构实测和路径设计。

## 5. 团队分工与系统数据流

| 模块 | 当前责任划分 | 应交付的结果 |
| --- | --- | --- |
| 机械结构 | 机械同学 | 可执行的推拨、下落、存储结构，以及尺寸、原点、行程和动作说明 |
| STM32 固件与运动 | 负责 STM32 的队友 | 串口解析、回零、坐标换算、驱动电机与舵机、转盘对位、限位与落料反馈 |
| 视觉识别 | 用户 | 物体位置、颜色、真实形状、表面信息和分类结果 |
| 通信与上位机调度 | 用户 | 协议、指令收发、单件任务调度、显示、计数和日志 |
| 分类口径与联调 | 团队共同确认 | 同类判定、盒号规则、坐标定义、完成判据与异常处理方式 |

当前原型采用下面的数据流：

```text
相机拍照
  → 识别物体的位置和属性
  → 选择本次目标、确定类别和盒号
  → 把像素坐标转换为托盘坐标
  → 通过串口发送 SORT(x, y, bin)
  → STM32 完成转盘对位、拨板移动及下落动作
  → STM32 返回完成结果
  → 上位机更新计数、图片、记录
  → 重新拍照，处理下一件
```

上位机当前发送的是“物体参考中心 + 目标盒号”。电机走多少步、拨板从哪里接触、如何转到目标盒，归 STM32 端实现。若实物表明路径规划需要全场障碍物信息，需进一步协商职责并扩展接口。

“确认入盒”只说明约定的物理动作结果，并不能证明视觉类别判定正确；两部分要分别验证。

## 8. 通信与坐标约定的第一版

这些约定已经体现在 Python 代码和模拟器中，尚未与真实 STM32 固件联调。实施时以 [通信协议文档](docs/通信协议.md) 为详细依据，调整后同步修改双方实现。

| 项目 | 当前约定 |
| --- | --- |
| 串口 | 115200，8N1，无流控；计划使用 USB 转 TTL |
| 报文 | ASCII 文本，`@1,SESSION,SEQ,CMD,参数...*CRC\r\n`，最长 256 字节 |
| 校验 | CRC-16/CCITT-FALSE；覆盖 `@` 后至 `*` 前的 ASCII 字节 |
| 任务标识 | SESSION 为会话，SEQ 为递增编号；重发保留相同编号与内容 |
| 主要命令 | HELLO、STATUS、HOME、SORT、RESULT、STOP、CLEAR_FAULT |
| 分拣指令 | `SORT,x,y,bin`，表示目标物体中心和目标盒号 |
| 坐标 | 托盘左下为原点，X 向右、Y 向上；与机械原点的对应关系待确定 |
| 传输单位 | x、y 为整数，单位 0.01mm；12500 表示 125mm，传输单位不代表定位精度 |
| 盒号 | 当前 1～6；盒号与转盘实际位置的对应由固件实现 |
| 接受任务 | `ACK,SORT` 只表示已接受，不能立即计数 |
| 成功结果 | `DONE,SORT,ENTRY_VERIFIED` 表示按约定判据确认入盒，上位机据此计数 |
| 未知结果 | 通过 RESULT 查询；设备复位或结果未知时，不自动重新执行一遍分拣 |

示意报文（省略完整帧头和校验）：

```text
上位机 → SORT,12500,8000,2
STM32  → ACK,SORT
STM32  → DONE,SORT,ENTRY_VERIFIED
```

STM32 必须对同一 `(SESSION, SEQ)` 的相同请求返回缓存状态或结果，避免重发导致电机重复执行。运动过程中仍需响应 STOP、STATUS 和 RESULT。

`ENTRY_VERIFIED` 的实物判据尚未确定。不能仅凭电机脉冲发完就认为物体已经入盒；需要结合转盘到位、物体通过与最终存储情况定义。现有软件停止还需要固件配合，硬件急停方案另由电控与机械同学落实。

| 单盒容量 | 4 | 软件配置值，没有实物容量验证 |
| 本轮时限 | 180 秒 | 暂按草稿；当前从首次运行开始计时，单件操作间等待也计入 |
| ACK 等待与重发 | 0.3 秒，最多重发 2 次 | 第一版通信参数，可按实机耗时调整 |
| 状态和结果轮询 | 约 0.5 秒 | 当前客户端实现 |
| 单动作时限 | 默认 12 秒，并受本轮剩余时间约束 | 需按实际机构速度及竞赛规则调整 |

四点标定按图像中的左上、右上、右下、左下选择托盘角点，保存到 `configs/calibration.json`。相机位置或图像分辨率变化需重新检查标定；平面映射还会受物体高度和镜头畸变影响。

### 9.2 视觉模块接入方式

后续识别器沿用 `detect(image) -> list[Detection]`，当前字段包括：

- `center`：物体参考中心，像素坐标。
- `bbox`：边框 `(x, y, w, h)`。
- `color`：颜色。
- `shape`：形状；真实模式应给实物类别，而非仅给二维轮廓。
- `shape_verified`：该形状输出是否已经过实物验证。
- `surface`：表面信息类型，目前可约定 none、stain、defect、text、qr 等。
- `surface_value`：文字、二维码内容或分类需要的其他值。

当前真实模式的分类键为 `(color, shape, surface, surface_value)`，按本轮首次出现的类别依次分配盒号。是否需要区分不同二维码内容、不同文字、不同图案，以及一个物体同时有多种表面信息时如何表示，均待规则确认。不要为了接通流程就把未验证的轮廓结果标成真实形状，或把看不见的信息填成“无”。

超过现有盒数的新类别、盒子达到配置容量、未知入盒结果都会中止推进。静态图片用于分析；真实分拣需要重新拍照。当前未实现程序重启后恢复盒号映射和计数，重新连接也不代表物理盒子已清空。

第一版开发时，以下 9 项自动化测试已经通过；本次只整理交接文档，没有重新运行测试或修改程序：

## 12. 建议的下一步顺序

1. **统一实物方案和规则。** 先补齐上表中“先确认”的信息，确定实际类别、坐标、盒号和一次分拣的动作定义。
2. **独立联调串口。** STM32 先实现 HELLO、STATUS、HOME、STOP，再实现 SORT 与 RESULT；使用固定坐标和固定盒号验证。
3. **跑通一个真实物体。** 固定位置、固定类别，验证转盘、拨板、下落反馈和上位机计数。
4. **建立小型实物照片集。** 保留原图和标注，覆盖不同位置、方向、光照、遮挡及相似类别，再据此决定传统视觉与模型各自承担什么任务。目前未确定具体模型路线。
5. **接入真实识别与标定。** 先确认识别正确，再检查坐标误差，最后扩展到多类别、随机摆放。
6. **部署到现场设备。** 验证香橙派的相机、串口和性能，调整 1024×600 屏幕布局与操作方式，接入比赛启动机制。
7. **记录整轮结果。** 分别记录分类准确率、实际入盒成功率、定位误差、单件耗时和异常原因，用结果决定优先改哪一块。

## 13. 接手后如何运行和共享

本机直接双击工程内的 `启动程序.cmd`，点击“自动运行”可体验模拟流程。在工程目录打开 PowerShell 也可运行：

```powershell
.\.venv\Scripts\python.exe -m sorting_app
.\.venv\Scripts\python.exe -m sorting_app --headless
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

换电脑时安装 Python 3.11 或更新版本，复制工程源代码、配置、文档、依赖清单和启动脚本，再运行 `一键安装环境.cmd`。`.venv` 不适合直接跨电脑复制。本机虚拟环境创建时复用了已有 OpenCV 和 NumPy，新电脑应重新安装依赖。
